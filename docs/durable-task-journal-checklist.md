## Границы текущего журнала исполнения (PR #4)

- Runtime: `ContextExecution → AgentLoopRunner → checkpointExecutions` сохраняет trace и журнал в одной SQLite-транзакции. Группа содержит план вызовов; `_started_calls` отмечает только исполнение, которое сейчас начнётся. До входа в executor его статус UNKNOWN уже записан. Результат сохраняется перед следующим вызовом.
- Идентификатор исполнения — UUID trace + ID вызова модели; повторяющийся ID модели в другом раунде не перезаписывает запись. Gate исключает только текущий execution, поэтому неопределённый повтор в том же раунде тоже блокируется.
- Gate сравнивает JSON-объекты по отсортированным ключам, сохраняя строки и порядок массивов. Старые записи тоже сравниваются канонически. Это сравнение одинаковых аргументов, не доказательство семантической эквивалентности разных операций.
- Повтор доверенных встроенных чтений разрешён; `todo` с `steps` считается записью. Незнакомые инструменты считаются потенциально опасными. Безопасное чтение может повторно стоить API-токенов/запросов; exactly-once оплаты не обещается.
- Timeout сохраняет UNKNOWN, даже если tool вернул timeout-ошибку. SUCCEEDED/FAILED — подтверждённый ответ исполнителя; FAILED не доказывает отсутствие внешнего побочного эффекта. Устаревшие checkpoints не могут стереть/подменить записанный результат.
- Тесты моделируют сбой после побочного действия, повторное открытие файла SQLite и реальный `ContextExecution`, блокировку повторного вызова, безопасное чтение, неначатые вызовы, одинаковые model IDs, атомарный rollback и сохранение trace/results.
- Это **не exactly-once**: нет общей транзакции с внешним сервисом, общего внешнего idempotency key или механизма подтверждённого разрешения UNKNOWN. Локальные persistent task/run/step и canonical operation key описаны ниже. После UNKNOWN опасная операция останавливается до проверки результата; автоматическое возобновление произвольной внешней записи не заявляется. Конкурирующие исполнители вне очереди приложения отдельно не поддержаны.

### Расширение persistent task/run/step (после проверки UNKNOWN)

SQLite v9 хранит отдельные задачи, связанные пользовательские сообщения, запуски с
parent_run_id, стабильные шаги по task + canonical operation key, результаты и file_refs,
связи вызовов с task/run/step и резервы модельных расходов. Повтор того же сообщения,
«далее» и ответ на ask_user продолжают задачу; новая содержательная команда начинает
новую задачу. ANSWERED означает, что ответ завершён, а не что модель доказала цель.

Подтверждённый SUCCEEDED записи в **той же задаче** возвращается инструментальному
циклу из SQLite, без повторного executor. Безопасные чтения выполняются заново для
актуальности. UNKNOWN по-прежнему блокируется, включая старые записи до v9; исторические
SUCCEEDED без task identity не приписываются новой задаче автоматически. Новый явный
запрос допускает намеренное новое действие; семантически разные аргументы не считаются
одной операцией. Это локальное возобновление с replay подтверждённых результатов,
не exactly-once внешнего сервиса.

Бюджет модели сохраняется между попытками: фактический usage заменяет резерв, а при
неизвестном исходе сохраняется консервативный резерв. Неизвестная предыдущая денежная
стоимость не может превратиться в ноль при включении USD-лимита. Эмбеддинги учитываются
отдельно; их расходы явно показываются как отдельные от бюджета генерации.

Статусы todo задаются агентом и не доказывают внешнее действие; подтверждённые результаты исполнителей показаны отдельно. Фоновый индекс копит batch 16; ручная индексация отправляет неполный остаток. Неизвестная стоимость не равна нулю.
